## Part 0: 왜 이걸 알아야 하는가

### AI 코딩 도구의 현실

```
2023년: "AI가 코드를 짜준다고?"
2024년: "AI 없이 어떻게 코딩했지?"
2025년: "AI를 잘 쓰는 사람 vs 못 쓰는 사람"
```

**핵심 메시지**: AI 코딩 도구는 이제 선택이 아닌 필수. 하지만 **잘 쓰는 방법**을 모르면 오히려 생산성이 떨어진다.

### 이 가이드의 목표

1. AI 코딩 도구가 **왜** 작동하는지 이해 (배경 이론)
2. AI와 함께 앱을 만드는 **워크플로우** 습득
3. 효과적인 **프롬프트 패턴** 학습
4. **흔한 실수**를 피하는 방법

## Part 1: 배경 이론

> "도구가 왜 작동하는지 알아야 잘 쓸 수 있다"

### 1.1 토큰 (Token)

**개념**: LLM은 텍스트를 "토큰"이라는 조각으로 쪼개서 처리한다.

```
"Hello, world!" → ["Hello", ",", " world", "!"]  (4 토큰)
"안녕하세요"     → ["안", "녕", "하", "세", "요"]  (5 토큰)
```

**왜 중요한가**:
| 영향 | 설명 |
|------|------|
| **비용** | 토큰 수 = 비용. 한글은 영어보다 ~3배 더 많은 토큰 사용 |
| **속도** | 토큰이 많을수록 응답 시간 증가 |
| **한계** | 컨텍스트 윈도우 내에서만 처리 가능 |

**실습**: [OpenAI Tokenizer](https://platform.openai.com/tokenizer)에서 직접 확인해보기

---

### 1.2 컨텍스트 윈도우 (Context Window)

**개념**: LLM이 한 번에 "볼 수 있는" 텍스트의 최대 크기

**비유: 책상 위 작업 공간**
```
┌─────────────────────────────────────┐
│         컨텍스트 윈도우              │
│  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐   │
│  │시스템│ │대화 │ │코드 │ │질문 │   │
│  │프롬프트│ │히스토리│ │파일 │ │    │   │
│  └─────┘ └─────┘ └─────┘ └─────┘   │
│                                     │
│  ⚠️ 꽉 차면 오래된 내용이 밀려남      │
└─────────────────────────────────────┘
```

**모델별 컨텍스트 크기**:
| 모델 | 컨텍스트 | 비유 |
|------|----------|------|
| GPT-3.5 | 16K 토큰 | A4 용지 20장 |
| GPT-4 | 128K 토큰 | 책 한 권 |
| Claude 3.5 | 200K 토큰 | 두꺼운 논문집 |
| Gemini 2.5 | 1M 토큰 | 도서관 한 섹션 |

**실전 팁**:
- 긴 대화 후 AI가 처음 지시를 잊는다면? → 컨텍스트 오버플로우
- 해결책: 중요한 지시는 다시 언급하거나, 새 대화 시작

---

### 1.3 Temperature (창의성 다이얼)

**개념**: AI 응답의 "무작위성"을 조절하는 설정

```
Temperature 0.0  ────────────────────  Temperature 1.0
     │                                      │
   예측 가능                              창의적
   항상 같은 답                          매번 다른 답
   코드 생성에 적합                       브레인스토밍에 적합
```

**실전 적용**:
| 작업 | 권장 Temperature |
|------|-----------------|
| 코드 생성 | 0.0 ~ 0.3 |
| 버그 수정 | 0.0 |
| 아이디어 발상 | 0.7 ~ 1.0 |
| 문서 작성 | 0.3 ~ 0.5 |

### 1.4 핵심 패턴들

#### RAG (Retrieval-Augmented Generation)

**비유**: 오픈북 시험

```
일반 LLM:        "내가 아는 것만으로 답할게" (환각 위험)
RAG 적용 LLM:    "관련 문서 찾아보고 답할게" (정확도 향상)
```

**동작 방식**:
```
질문 → 관련 문서 검색 → 검색 결과 + 질문 → LLM → 답변
```

**활용 예시**:
- 회사 내부 문서 기반 Q&A
- 최신 정보가 필요한 질문
- 도메인 특화 지식 필요할 때

---

#### Function Calling / Tool Use

**비유**: 매니저와 직원들

```
사용자: "서울 날씨 알려줘"

LLM (매니저): "이건 내가 직접 못해. 날씨 API 호출해야겠다"
     ↓
Tool (직원): get_weather("서울") → {"temp": 15, "condition": "맑음"}
     ↓
LLM: "서울은 현재 15도이고 맑습니다"
```

**Claude Code가 파일을 읽고 수정하는 원리**:
```
사용자: "이 버그 수정해줘"
     ↓
Claude: read_file("main.py") 호출
     ↓
Claude: 코드 분석 후 edit_file() 호출
     ↓
Claude: "수정 완료했습니다"
```

---

#### Agent 패턴

**비유**: 자율적인 인턴

```
일반 LLM:  질문 → 답변 (1회성)

Agent:     목표 → 계획 → 실행 → 관찰 → 계획 수정 → 실행 → ... → 완료
```

**Agent의 동작 루프 (ReAct)**:
```
1. Think:   "무엇을 해야 하지?"
2. Act:     도구 실행 (파일 읽기, 검색, 코드 실행)
3. Observe: 결과 확인
4. Repeat:  목표 달성까지 반복
```

**Claude Code, Gemini CLI가 Agent인 이유**:
- 스스로 파일 탐색
- 필요한 정보 검색
- 코드 수정 후 테스트 실행
- 에러 발생 시 자동 수정 시도

---

#### MCP (Model Context Protocol)

**비유**: USB-C 표준

```
Before MCP:  각 도구마다 다른 연결 방식 (혼란)
After MCP:   표준화된 연결 방식 (일관성)
```

**개념**: AI가 외부 도구와 통신하는 **표준 프로토콜** (Anthropic 개발)

```
┌─────────┐     MCP      ┌─────────────┐
│  Claude │ ←──────────→ │  DB Server  │
│         │              │  API Server │
│         │              │  File System│
└─────────┘              └─────────────┘
```

**왜 중요한가**:
- 한 번 만든 MCP 서버는 모든 MCP 지원 AI에서 사용 가능
- 사내 시스템을 AI와 쉽게 연결 가능

### 2.1 SPEC (문서화)

#### 핵심 원칙

> **"AI는 모호함을 채우는 컴파일러"**
> 
> 스펙이 모호하면 AI가 마음대로 해석한다. 그리고 그 해석은 대부분 틀리다.

#### 역할 분담

| Human | AI |
|-------|-----|
| 요구사항 정의 | 스펙 작성 보조 |
| 비즈니스 로직 결정 | 빠진 부분 찾기 |
| 최종 승인 | 모호함 지적 |

#### AI가 잘 이해하는 스펙 구조

```markdown
## 1. 목표 (Goal)
이 기능이 해결하는 문제

## 2. 비목표 (Non-Goals)  ← 매우 중요!
이 기능에서 하지 않는 것

## 3. 유저 스토리
- 사용자는 ~할 수 있다
- 관리자는 ~할 수 있다

## 4. 기능 요구사항
- [ ] 구체적인 기능 1
- [ ] 구체적인 기능 2

## 5. 엣지 케이스
- 입력값이 없을 때: ~
- 네트워크 에러 시: ~

## 6. 성공 기준
- 응답 시간 < 200ms
- 에러율 < 0.1%
```

#### 나쁜 스펙 vs 좋은 스펙

**나쁜 스펙**:
```
사용자가 리포트를 내보낼 수 있어야 함
```

**좋은 스펙**:
```markdown
## 리포트 내보내기

### 지원 포맷
- PDF (A4, 세로 방향)
- CSV (UTF-8, 쉼표 구분)

### 제약 조건
- 10,000행 이하 리포트: 5초 이내 완료
- 현재 적용된 필터와 정렬 반영
- 숨겨진 컬럼은 제외

### 엣지 케이스
- 데이터 없음: "내보낼 데이터가 없습니다" 메시지
- 내보내기 중 에러: 재시도 버튼 표시
```

#### AI 활용 프롬프트

**스펙 검토 요청**:
```
이 스펙을 검토해줘:
- 모호한 부분
- 빠진 엣지 케이스
- 암묵적으로 가정하고 있는 것

기능 추가 제안은 하지 마.
```

**스펙 완성도 체크**:
```
이 스펙을 구현하기 전에 개발자가 물어볼 것 같은 질문들을 나열해줘.
```

### 2.2 DEVELOP (개발)

#### 핵심 원칙

> **"AI는 주니어 개발자"**
> 
> 빠르게 코드를 만들어내지만, 결과물은 반드시 시니어가 리뷰해야 한다.

#### 역할 분담

| Human | AI |
|-------|-----|
| 아키텍처 결정 | 코드 생성 |
| 코드 리뷰 | 보일러플레이트 작성 |
| 패턴 가이드 | 반복 작업 |

#### 프로젝트 컨텍스트 설정

**`CLAUDE.md` (또는 `.cursorrules`) 예시**:

```markdown
# 프로젝트 개요
Next.js 14 App Router + TypeScript + Tailwind CSS

# 아키텍처
- /app: 페이지 및 라우트
- /components: 재사용 컴포넌트
- /lib: 유틸리티 함수
- /hooks: 커스텀 훅

# 코딩 컨벤션
- 함수형 컴포넌트만 사용
- Props는 interface로 정의
- 에러 처리는 try-catch + Error Boundary

# 금지 패턴
- any 타입 사용 금지
- console.log 프로덕션 코드에 금지
- 인라인 스타일 금지

# 새 기능 추가 시
1. 스펙 문서 먼저 작성
2. 테스트 코드 작성
3. 구현
4. 리뷰
```

#### 개발 순서

```
1. 스펙을 작은 단위로 분할
   └─ "전체 기능 만들어줘" (❌)
   └─ "로그인 폼의 validation 로직만 만들어줘" (✅)

2. 기존 코드 패턴 보여주기
   └─ "이 프로젝트의 다른 폼 컴포넌트처럼 만들어줘"

3. 제약 조건 명시
   └─ "기존 API 인터페이스는 변경하지 마"

4. 생성된 코드 리뷰
   └─ 모든 코드를 직접 읽고 이해
```

#### AI 활용 프롬프트

**기능 구현**:
```
다음 스펙을 구현해줘: [스펙]

제약 조건:
- 기존 컴포넌트 스타일 따르기 (Button.tsx 참고)
- 새 의존성 추가 금지
- 에러 처리 포함

먼저 구현 계획을 설명하고, 승인 후 코드 작성해줘.
```

**코드 설명 요청**:
```
이 코드가 뭘 하는지 설명해줘.
왜 이렇게 구현했는지도 알려줘.
```

### 2.3 TEST (테스트)

#### 핵심 원칙

> **"AI가 만든 테스트도 틀릴 수 있다"**
> 
> 테스트가 정말로 의도한 동작을 검증하는지 사람이 확인해야 한다.

#### 역할 분담

| Human | AI |
|-------|-----|
| 테스트 의도 정의 | 테스트 코드 생성 |
| assertion 검증 | 엣지 케이스 확장 |
| 테스트 품질 확인 | 보일러플레이트 작성 |

#### TDD with AI

```
1. Human: 테스트해야 할 동작 정의
   "로그인 시 잘못된 비밀번호면 에러 메시지 표시"

2. AI: 테스트 코드 생성
   test("shows error on wrong password", ...)

3. Human: 테스트 로직 검증
   "이 테스트가 정말 에러 메시지를 확인하나?"

4. AI: 테스트 통과하는 코드 구현

5. CI: 테스트 실행 + mutation testing
```

#### AI 활용 프롬프트

**테스트 생성**:
```
이 함수에 대한 테스트를 작성해줘.

가정:
- 구현이 틀렸다고 가정하고 테스트 작성
- 엣지 케이스와 실패 시나리오에 집중
- 각 테스트가 무엇을 검증하는지 주석으로 설명

포함해야 할 케이스:
- 정상 입력
- 빈 입력
- 잘못된 형식
- 경계값
```

**테스트 커버리지 확장**:
```
현재 테스트에서 빠진 케이스를 찾아줘.
특히 실패할 수 있는 시나리오를 중점적으로.
```

### 2.4 VERIFY (검증)

#### 핵심 원칙

> **"AI 리뷰는 1차 필터, 사람 리뷰가 최종"**
> 
> AI는 명백한 실수를 빠르게 잡고, 사람은 비즈니스 로직과 의도를 검증한다.

#### 역할 분담

| Human | AI |
|-------|-----|
| 비즈니스 로직 검증 | 스타일/포맷 체크 |
| 의도 확인 | 명백한 버그 찾기 |
| 최종 승인 | 보안 패턴 체크 |

#### 검증 레이어

```
┌────────────────────────────────────────┐
│  Layer 1: AI 자동 리뷰                  │
│  - 린트 에러, 타입 에러                 │
│  - 명백한 버그 패턴                     │
│  - 스타일 가이드 위반                   │
└────────────────────────────────────────┘
                ↓
┌────────────────────────────────────────┐
│  Layer 2: Human 리뷰                   │
│  - 비즈니스 로직 정확성                 │
│  - 코드 의도와 스펙 일치               │
│  - 아키텍처 적합성                     │
└────────────────────────────────────────┘
                ↓
┌────────────────────────────────────────┐
│  Layer 3: CI 자동화                    │
│  - 테스트 실행                         │
│  - 타입 체크                           │
│  - 빌드 확인                           │
└────────────────────────────────────────┘
                ↓
┌────────────────────────────────────────┐
│  Layer 4: Mutation Testing (선택)      │
│  - 테스트가 진짜 버그를 잡는지 확인     │
└────────────────────────────────────────┘
```

#### AI 활용 프롬프트

**코드 리뷰 요청**:
```
이 코드를 리뷰해줘.

가정:
- 이 코드가 프로덕션에서 실패한다고 가정
- 칭찬 말고 리스크만 알려줘
- 정확성에 집중, 스타일은 무시

특히 확인해줘:
- 에러 처리 누락
- 엣지 케이스 미처리
- 보안 취약점
- 성능 이슈
```

**스펙 대비 검증**:
```
이 구현이 다음 스펙을 만족하는지 확인해줘:
[스펙]

만족하지 않는 항목이 있으면 구체적으로 알려줘.
```

## Part 3: 프롬프트 패턴

> "좋은 프롬프트 = 좋은 결과"

### 3.1 기본 원칙

| 원칙 | 나쁜 예 | 좋은 예 |
|------|--------|--------|
| **구체적으로** | "이거 고쳐줘" | "Line 42의 null 체크 누락 수정해줘" |
| **제약 조건 명시** | "리팩토링해줘" | "public API 유지하고 내부만 정리해줘" |
| **단계별 요청** | "전체 기능 만들어줘" | "1단계: 타입 정의, 2단계: API, 3단계: UI" |
| **역할 부여** | (없음) | "시니어 개발자로서 리뷰해줘" |
| **출력 형식 지정** | (없음) | "JSON으로 응답해줘" |

---

### 3.2 상황별 프롬프트 템플릿

#### 버그 수정

```
## 문제
[예상 동작] vs [실제 동작]

## 에러 메시지
[정확한 에러 메시지 / 스택 트레이스]

## 관련 코드
[코드 붙여넣기]

## 이미 시도한 것
- 시도 1: [결과]
- 시도 2: [결과]

## 요청
1. 먼저 근본 원인을 분석해줘
2. 그 다음 최소한의 수정안을 제시해줘
3. 관련 없는 코드는 건드리지 마
```

#### 새 기능 구현

```
## 스펙
[기능 설명]

## 제약 조건
- [제약 1]
- [제약 2]

## 참고할 기존 코드
[비슷한 기존 구현 경로]

## 요청
1. 먼저 구현 계획을 설명해줘
2. 내가 승인하면 코드 작성해줘
3. 한 번에 전체 말고, 단계별로 진행해줘
```

#### 코드 리뷰

```
## 코드
[코드 붙여넣기]

## 컨텍스트
- 이 코드의 목적: [설명]
- 관련 스펙: [링크 또는 설명]

## 리뷰 요청
이 코드가 프로덕션에서 문제를 일으킬 거라고 가정하고 리뷰해줘.

집중해서 볼 것:
- 에러 처리
- 엣지 케이스
- 성능
- 보안

칭찬이나 스타일 코멘트는 필요 없어.
```

#### 리팩토링

```
## 현재 코드
[코드 붙여넣기]

## 리팩토링 목표
[가독성 개선 / 성능 개선 / 구조 개선]

## 제약 조건
- 동작은 100% 동일하게 유지
- public 인터페이스 변경 금지
- 새 의존성 추가 금지

## 요청
작은 단계로 나눠서 리팩토링해줘.
각 단계마다 무엇을 바꾸는지 설명해줘.
```

### 3.3 고급 패턴

#### Chain of Thought (단계별 사고)

```
이 문제를 단계별로 분석해줘:

1. 먼저 문제를 정확히 이해했는지 확인
2. 가능한 원인들을 나열
3. 각 원인의 가능성을 평가
4. 가장 가능성 높은 원인에 대한 해결책 제시

각 단계를 명시적으로 보여줘.
```

#### Few-shot (예시 제공)

```
다음 형식으로 에러 메시지를 작성해줘:

예시 1:
입력: 이메일 형식 오류
출력: "올바른 이메일 주소를 입력해주세요. (예: user@example.com)"

예시 2:
입력: 비밀번호 길이 부족
출력: "비밀번호는 최소 8자 이상이어야 합니다."

이제 작성해줘:
입력: 전화번호 형식 오류
출력:
```

#### 역할 부여 (Role Prompting)

```
너는 10년차 시니어 백엔드 개발자야.
보안과 성능에 특히 민감하고, 코드 리뷰할 때 꼼꼼하게 본다.

다음 코드를 리뷰해줘:
[코드]
```

## Part 4: 흔한 실수와 함정

### 4.1 AI 맹신

| 실수 | 결과 | 해결책 |
|------|------|--------|
| AI 답변 무조건 수용 | 버그, 보안 취약점 | 모든 코드 직접 리뷰 |
| "AI가 맞다고 했으니까" | 책임 회피 불가 | 최종 책임은 개발자 |

**명심할 것**:
> AI는 "그럴듯하게 틀릴 수 있다" (Confidently Wrong)

---

### 4.2 컨텍스트 부족

| 실수 | 결과 | 해결책 |
|------|------|--------|
| 코드만 던지기 | 엉뚱한 수정 | 배경, 제약조건 함께 제공 |
| 에러 메시지 생략 | 추측성 답변 | 정확한 에러 복붙 |

**좋은 컨텍스트 체크리스트**:
- [ ] 무엇을 하려고 했나?
- [ ] 무엇이 잘못됐나?
- [ ] 정확한 에러 메시지는?
- [ ] 어떤 제약 조건이 있나?
- [ ] 이미 시도한 것은?

---

### 4.3 범위 관리 실패

| 실수 | 결과 | 해결책 |
|------|------|--------|
| "전체 앱 만들어줘" | 품질 저하 | 작은 단위로 분할 |
| 한 번에 너무 많은 요청 | 일부만 처리됨 | 하나씩 순차적으로 |

**좋은 요청 크기**:
```
❌ "로그인 시스템 전체 만들어줘"
✅ "로그인 폼의 이메일 validation 로직 만들어줘"
```

---

### 4.4 학습 기회 상실

| 실수 | 결과 | 해결책 |
|------|------|--------|
| 복붙만 하기 | 실력 정체 | "왜 이렇게 했어?" 물어보기 |
| 이해 없이 사용 | 디버깅 불가 | 코드 설명 요청 |

**성장하는 AI 활용법**:
```
1. AI가 코드 생성
2. "이 코드가 뭘 하는지 설명해줘"
3. "왜 이 방식을 선택했어?"
4. "다른 방법은 없어?"
5. 이해한 후 적용
```

---

### 4.5 보안 실수

| 실수 | 위험 | 해결책 |
|------|------|--------|
| API 키 프롬프트에 포함 | 키 노출 | 환경 변수 사용 |
| 민감 코드 공유 | 정보 유출 | 사내 보안 정책 준수 |

**절대 프롬프트에 포함하지 말 것**:
- API 키, 비밀번호
- 고객 개인정보
- 사내 기밀 로직

## 마무리

AI 코딩 도구는 **생산성을 크게 높여주는 강력한 도구**다.

하지만 잘 쓰려면:
1. **원리를 이해**하고 (Part 1)
2. **체계적인 워크플로우**를 따르고 (Part 2)
3. **효과적인 프롬프트**를 사용하고 (Part 3)
4. **흔한 실수를 피해야** 한다 (Part 4)

> **"AI가 코드를 짜주는 시대. 하지만 좋은 코드는 여전히 사람의 판단에서 나온다."**
